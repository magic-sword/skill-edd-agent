# 仮想環境（Sandbox）とシミュレーション評価の設計思想 (Evaluation Design)

本ドキュメントでは、`edd-agent-tools` パッケージにおける「テスト実行環境の完全隔離」および「多層シミュレーション評価におけるバウンダリーとアサーション設計」のアーキテクチャ思想について解説します。

---

## 1. 開発環境の完全隔離（関心の分離とサンドボックス）

自動コーディングエージェントやテスト実行器がファイルシステムを操作し、テスト（例: `pytest`）を実行する際、実環境に直接変更をアプライすると、意図しない破壊やテスト中の競合などの深刻な問題が発生します。

本システムでは、**「隔離された環境でのテスト検証（シミュレーション）」** と **「本番環境への安全な反映（永続化）」** の責務を完全に分離しています。

```
     [Real Workspace]
            │
            ├─ 1. Clone (Temporary Dir) ──► [LocalWorkspaceEnv (Git Sandbox)]
            │                                             │
            │                                     2. Run Actions & Test
            │                                             │
            ├─ 4. Apply changes ◄── 3. Export Artifact ───┘
```

1.  **環境のクローンと隔離 (`LocalWorkspaceEnv`)**:
    テスト実行開始時、本番ディレクトリから OS の一時ディレクトリ領域（`/tmp` 等）に作業コピーを複製し、そこをカレントとしてプロセスを動かします。
2.  **Git による高速ステート管理**:
    隔離環境内は自動的に Git リポジトリとして初期化されます。これにより以下の恩恵が得られます：
    *   **高速ロールバック**: テストケースの実行ごとにミリ秒単位で完全に初期状態へ環境を復元できます。
    *   **正確な差分抽出**: テスト成功後、`git status` を解析することで、作成・修正・削除されたファイル群（`WorkspaceArtifacts`）のみを正確に抽出できます。
3.  **安全な本番適用**:
    すべての検証に合格し、安全が確認された段階でのみ、抽出した差分（`WorkspaceArtifacts`）を明示的に本番の `Real Workspace` に反映します。これにより、破壊的なコードが本番に直接混入するリスクを根絶しています。

---

## 2. インプロセス・インテント分類シミュレーションによる評価設計

### 設計方針
トリガー評価（インテント判定）においては、エージェント基底プロセスや一時ファイルの動的生成を行わず、**「登録されているスキルの仕様情報（`SKILL.md`）を読み込んで LLM に選択させるインテント分類器」** をインプロセスで実行します。

*   **高速・軽量**: 一時ファイルの物理生成が一切不要で、ファイルIOのオーバーヘッドを極小化。
*   **決定論的アサーション**: アサーションロジックをPythonコード側で完全に制御し、負例ケースにおける誤起動の検出（正しく起動対象外になったことの検証）が極めて正確に行えます。

---

## 3. アサーションの決定論的評価設計

テストの関心事を分離し、テストを安定（デバッガブル）にするため、評価パターンに応じて判定ポリシーを適切に整理しています。

| 評価パターン | 主な検証目的 | 判定ポリシー（合否の基準） |
| :--- | :--- | :--- |
| **契約テスト (Contract / CLI)** | スクリプトおよびCLIツールの決定論的I/O動作の正しさ。 | 入力引数（`cli_args`）に応じた終了コード（`expected_exit_code`）および標準出力キーワード（`expected_stdout_contains`）の Black-box 決定論的検証。 |
| **トリガー評価 (Trigger)** | LLMのインテント分類の意思決定（適切なスキルを起動できるか）。 | **正例**: 対象スキルが選択されれば合格。<br>**負例**: 対象スキルが「選択されなければ（不一致なら）」、他のどのスキルが選ばれても（あるいは None でも）誤起動を防げたため合格。 |
| **ゴールデン評価 (Golden / Trajectory)** | 出力結果の妥当性、およびワークフローにおける実行経路の正しさ。 | **出力アサーション**: 最終回答の意味的整合性（LLM Judge）。<br>**経路アサーション**: `expected_trajectory`（期待されるツール呼び出しのシーケンスおよび引数目的）を適切に辿っているか。 |

このアサーション設計により、LLM の持つ確率的な揺れを吸収しつつ、「システム全体のルーティングが破綻していないか」と「対象スキルのトリガー具体性が担保されているか」を、極めて高速かつ安定して検証できます。
