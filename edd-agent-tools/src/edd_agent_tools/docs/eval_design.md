# 仮想環境（Sandbox）とシミュレーション評価の設計思想

本ドキュメントでは、`edd-agent-tools` パッケージにおける「テスト実行環境の完全隔離」および「シミュレーション評価におけるバウンダリーとアサーション設計」のアーキテクチャ思想について解説します。

---

## 1. 開発環境の完全隔離（関心の分離とサンドボックス）

自動コーディングエージェントやテスト実行器がファイルシステムを操作し、テスト（例: `pytest`）を実行する際、実環境に直接変更をアプライすると、意図しない破壊やテスト中の競合などの深刻な問題が発生します。

本システムでは、**「隔離された環境でのテスト検証（シミュレーション）」** と **「本番環境への安全なマージ（永続化）」** の責務を完全に分離しています。

```
     [Real Workspace]
            │
            ├─ 1. Clone (Temporary Dir) ──► [LocalWorkspaceEnv (Git Sandbox)]
            │                                             │
            │                                     2. Run Actions & Test
            │                                             │
            ├─ 4. Apply changes ◄── 3. Export Artifact ───┘
```

1.  **環境のクローンと隔離 (`LocalWorkspaceEnv`)**:
    テスト実行開始時、本番ディレクトリから OS の一時ディレクトリ領域（`/tmp` 等）に作業コピーを複製し、そこをカレントとしてプロセスを動かします。
2.  **Git による高速ステート管理**:
    隔離環境内は自動的に Git リポジトリとして初期化されます。これにより以下の恩恵が得られます。
    *   **高速ロールバック**: テストケースの実行ごとに `git reset --hard` / `git clean` を実行し、ミリ秒単位で完全に初期状態へ環境を復元できます。
    *   **正確な差分抽出**: テスト成功後、`git diff` または `git status` を解析することで、作成・修正・削除されたファイル群（`WorkspaceArtifacts`）のみを正確に抽出できます。
3.  **本番適用 (`LocalFileApplier`)**:
    すべての検証に合格し、安全が確認された段階で、アプライヤーを用いて抽出した差分（`WorkspaceArtifacts`）だけを明示的に本番の `Real Workspace` に書き戻します。これにより、破壊的なコードが本番に直接混入するリスクを根絶しています。

---

## 2. 旧 ADK 評価方式から「インテント分類シミュレーション」への移行

### 以前の課題（`adk eval` による密結合）
以前のインテント評価（旧 `trigger-evaluator`）は、ADK の公式評価器である `adk eval` を用いていました。
この方式には、以下の課題がありました。
1.  **評価用エージェントの動的生成のオーバーヘッド**: `adk eval` の制約を満たすため、一時ディレクトリに `agent.py` やモック用コード（`eval_mock_setup.py`）を動的にファイル生成・配置して実行する必要があり、インフラとして非常に重く、ファイルIOのオーバーヘッドが発生していた。
2.  **再現性の低さと引数アサーションの揺れ**: LLM のインテント検知結果だけでなく、引数プロンプトの完全一致まで ADK 評価器が要求するため、表記の揺れだけで不合格になり、決定論的な結果をテストすることが極めて困難であった。

### 解決策: オンデマンドなインテント分類シミュレーションへの移行
新テストアーキテクチャでは、重い `adk eval` や `agent.py` の物理生成を廃止し、**「登録されているスキルの仕様情報（`SKILL.md`）を読み込んで LLM に選択させるインテント分類器（`IntentClassifier`）」** を `trigger-test-executor` 内でインプロセス実行する形に刷新しました。

*   これにより、一時ファイルの物理生成が一切不要になり、テスト実行時間が大幅に短縮されました。
*   アサーションを Python コード側でコントロールできるため、負例ケースにおける誤起動の検出（正しく起動対象外になったことの検証）が極めて正確になり、再現性 100% の決定論的テストが可能になりました。

---

## 3. アサーションの決定論的評価設計

テストの関心事を分離し、テストを安定（デバッガブル）にするため、評価パターンに応じて判定ポリシーを適切に整理しています。

| 評価パターン | 主な検証目的 | 判定ポリシー（合否の基準） |
| :--- | :--- | :--- |
| **単体テスト (Unit / Schema)** | スキルの Python コードとしての動作の正しさ。 | 入力値に応じた戻り値の正しさ、および期待される例外アサーション（例: ValidationError 等の例外が正しくスローされるか）を検証。 |
| **トリガー評価 (Trigger)** | LLMのインテント分類の意思決定（適切なスキルを起動できるか）。 | **正例**: 対象スキルが選択されれば合格。<br>**負例**: 対象スキルが「選択されなければ（不一致なら）」、他のどのスキルが選ばれても（あるいは None でも）誤起動を防げたため合格。 |
| **ゴールデン評価 (Golden / Trajectory)** | 出力結果の妥当性、およびワークフローにおける実行経路の正しさ。 | **出力アサーション**: 最終回答の意味的整合性（LLM Judge）。<br>**経路アサーション**: `expected_trajectory`（期待されるツール呼び出しのシーケンスおよび引数目的）を適切に辿っているか。 |

このアサーション設計により、LLM の持つ確率的な揺れを吸収しつつ、「システム全体のルーティングが破綻していないか」と「対象スキルのトリガー具体性が担保されているか」を、極めて高速かつ安定して検証できるようになっています。
