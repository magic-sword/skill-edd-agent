# ADK 評価実行時における動的エージェント解決と規約の設計思想

本ドキュメントは、AIエージェントおよびスキルの評価（テスト）プロセスにおける結合度の排除（独立化）と、今回のリファクタリングで確立されたオブジェクト指向設計（ポリモーフィズム）およびテスト結果の後処理による安全なアサーション設計思想を解説したものです。

---

## 1. 背景と以前の課題

リファクタリング前、評価シミュレータ（`mock-executor` や `test-executor`）は、ADK評価器である `adk eval` に本番用エントリポイントである `src/agent.py`（およびモック結合用の `src/mock_entry`）のパスを渡して実行していました。

この設計には、以下の深刻な密結合の問題がありました。

1. **ポータビリティの欠如**: 本番用の `src/agent.py` や `mock_entry` が存在しないプロジェクト環境では評価を実行できない。また、本番コードの内部構造が変更されるとテスト側が壊れてしまう。
2. **評価環境でのポリシー切り替えの複雑さ**: テスト時のみモック用コールバック（`before_tool_callback`）を結合させるために、本番コードやテスト側で環境変数（`ADK_EVAL_MODE` 等）を用いた複雑な条件分岐の判定を行う必要があった。
3. **二重ラッパー問題（ワークフロー評価時）**: 評価対象がワークフロー（複数のエージェントやスキルの連携）である場合も、通常のスキルと同様に「汎用エージェントの `tools` にワークフロー全体を1つのツールとして突っ込んで評価する」形になっていた。このため、中間の汎用エージェントが仲介し、LLMの無駄な対話（ハルシネーションの発生余地）が発生していた。

---

## 2. 解決策：評価用エージェント環境の動的生成

`adk eval` の仕様として、**「指定されたディレクトリ（`agent_dir`）から `agent.py` をロードし、そこから `Agent` インスタンスを取得してクエリを投げる」** という物理的なファイル制約があります。

これをクリアしつつ、本番コードとの密結合を断ち切るため、**「評価時に一時ディレクトリ（`scratch/eval_run_...`）を作成し、評価種別・モードに特化した `agent.py` をその場で自動生成して配置する」** アプローチを採用しました。

これにより、本番コード（`/workspace/src`）への依存は完全にゼロになり、テスト実行側が自己完結してエージェント環境をシミュレートできるようになりました。

---

## 3. オブジェクト指向（ポリモーフィズム）によるテスト設計

今回のリファクタリングにおいて、手続き的な条件フラグ（`mock: bool` 等）を排除し、テストの挙動制御にオブジェクト指向のポリモーフィズムを徹底しました。

### ① テストエージェント構築のポリモーフィズム
`SkillEval` 基底クラスを抽象クラスとし、`UnitEval`（ユニットテスト用）と `TriggerEval`（トリガーテスト用）がそれぞれ独自の `generate_agent_code()` メソッドを実装することで、通常実行かモック結合コードかを自律的に決定して構築します。

*   **`UnitEval`**: モックを含まない、通常のベースエージェントテンプレートコードのみを生成。
*   **`TriggerEval`**: ベーステンプレートコードに、モックセットアップコード（`eval_mock_setup.py.tmpl`）を結合して生成。

### ② ツールモックのポリモーフィズム
トリガーテスト（インテント検知）におけるツールのモック化も、関数レベルの割り当てから、オブジェクトモデルによるポリモーフィズム設計へ移行しました。

*   **`ToolMock` (Protocol)**: 個々のツールのモック挙動をカプセル化するポリモーフィズム用インターフェース。
*   **`UniversalToolMock` (具象)**: `load_skill` および評価対象のカスタムツールを含むすべてのツールコールを安全にバイパスしつつ、ADKの合否判定に必要なステートへのトリガー履歴の記録（追跡）を自動で行う汎用モック。
*   **`MockEnvironment`**: 複数の `ToolMock` オブジェクトをリストとして保持・管理し、ADK用の統合コールバックを提供するコンテキスト。新しいモック対象ツールが増えた場合も、この環境を変更することなく、`ToolMock` を実装した具象クラスを新規追加して並べるだけで容易に拡張可能（オープン・クローズドの原則の遵守）。

## 4. テストの関心事の分離と引数無視アサーション（Post-Processing）

ADKおよび評価駆動開発（EDD）では、テストの「関心事の分離」を最大化するため、テストの目的（分類）に応じて実行ポリシーを切り替えます。

| 評価パターン | 主な検証目的 | 実行ポリシー | 判定ポリシーと整合 |
| :--- | :--- | :--- | :--- |
| **Trigger Check** | LLMのツール呼び出し意思決定（インテント検知） | **モック実行 (Mock)** | ツール名と呼び出し回数の一致のみを評価。プロンプトのような曖昧な引数は、LLMの揺れによるテストの不安定化を防ぐため **引数の値をアサーションから除外**。 |
| **Eval-as-Unit-Test** | ツールコードの実装の正しさ | **通常実行 (Real)** | 実実行。ツール自体をモック化せず、Pythonロジックそのものが正しい値や結果を出力するかを検証。 |

### 決定論的な結果の後処理 (Post-Processing)

ADK標準の軌跡評価器 `TrajectoryEvaluator` は引数（`args`）の完全等価比較（`==`）を要求するため、自然言語プロンプトの揺れがあると `score=0.0`（不合格）になります。

これを解決するために、ADKの非公開APIを上書きする危険なモンキーパッチや、コストのかかるLLM-as-a-Judgeに頼る車輪の再発明を行わず、**「テスト実行ランナー（`runner.py`）がADKの実行完了後に、返却された公開データ構造である `EvalCaseResult` を解析し、ツール名のみが一致していれば Passed に補正・再集計する後処理（Post-Processing）ロジック」** を導入しました。これにより、公式仕様の枠組みだけで、ミリ秒単位で高速かつ決定論的（100%再現可能）なトリガーテストを達成しています。

## 5. ワークフローエージェントの規約統一

ワークフロー全体の評価をダイレクトかつクリーンに行うため、以下の規約を義務化・統一しました。

### 統一規約
> モジュールタイプが **`WORKFLOW`** のパッケージ（例: `workflow-generator`）は、そのエントリーポイントである **`scripts/__init__.py`** から、**`workflow_agent`**（`Agent` オブジェクト実体）を必ずエクスポート（公開）しなければならない。

### 動作フロー
1. 動的生成される評価用の `agent.py` は、対象が `ModuleType.WORKFLOW` であることを検知すると、そのパッケージの `scripts/__init__.py` から `workflow_agent` を直接インポートします。
2. インポートした `workflow_agent` をそのまま `adk eval` にエクスポートします。
3. これにより、中間エージェントが噛まない「ダイレクトなワークフロー評価」が可能となり、二重ラッパー問題が完全に解消されます。

---

## 6. 物理テンプレートとフォルダ構成

動的生成するコード文字列のハードコーディング（ヒアドキュメント）を排除し、より安全かつ堅牢にするために以下のフォルダ構成を採用しています。

1. **`evaluation/` パッケージフォルダへの整理**:
   Python組み込みの `eval()` 関数との混同を避けるため、旧 `evaluation.py` ファイルを廃止し、**`edd_agent_tools/evaluation/`** パッケージフォルダ配下に評価関連クラスやアセットを集約・再配置しました。
2. **物理テンプレート（`*.tmpl`）による管理**:
   エージェント起動用のコードひな型を **`evaluation/templates/`** 配下に物理ファイルとして分離しました。
   - `eval_agent_skill.py.tmpl`（スキル評価用ベースコード）
   - `eval_agent_workflow.py.tmpl`（ワークフロー評価用ベースコード）
   - `eval_mock_setup.py.tmpl`（モックアタッチ用コード）
   - `eval_agent_init.py.tmpl`（一時パッケージ `__init__.py` 用コード）
3. **安全なプレースホルダー置換**:
   `SkillEval` 内では、テンプレートファイルをロードし、標準文字列フォーマット（`.format()`）を用いて必要なプレースホルダー（`{skill_name}`, `{skill_root}` など）のみを安全に置換します。これにより、インデントエラーやエスケープの問題といった動的生成時のバグのリスクを最小化しています。
