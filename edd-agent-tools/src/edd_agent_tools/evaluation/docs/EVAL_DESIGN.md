# ADK 評価実行時における動的エージェント解決と規約の設計思想

本ドキュメントは、AIエージェントおよびスキルの評価（テスト）プロセスにおける結合度の排除（独立化）と、ワークフローエージェントの定義規約に関する設計思想を解説したものです。

---

## 1. 背景と以前の課題

リファクタリング前、評価シミュレータ（`mock-executor` や `test-executor`）は、ADK評価器である `adk eval` に本番用エントリポイントである `src/agent.py`（およびモック結合用の `src/mock_entry`）のパスを渡して実行していました。

この設計には、以下の深刻な密結合の問題がありました：
1. **ポータビリティの欠如**: 本番用の `src/agent.py` や `mock_entry` が存在しないプロジェクト環境では評価を実行できない。また、本番コードの内部構造が変更されるとテスト側が壊れてしまう。
2. **評価環境でのポリシー切り替えの複雑さ**: テスト時のみモック用コールバック（`before_tool_callback`）を結合させるために、本番コードやテスト側で環境変数（`ADK_EVAL_MODE` 等）を用いた複雑な条件分岐の判定を行う必要があった。
3. **二重ラッパー問題（ワークフロー評価時）**: 評価対象がワークフロー（複数のエージェントやスキルの連携）である場合も、通常のスキルと同様に「汎用エージェントの `tools` にワークフロー全体を1つのツールとして突っ込んで評価する」形になっていた。このため、中間の汎用エージェントが仲介し、LLMの無駄な対話（ハルシネーションの発生余地）が発生していた。

---

## 2. 解決策：評価用エージェントディレクトリの動的生成

`adk eval` の仕様として、**「指定されたディレクトリ（`agent_dir`）から `agent.py` をロードし、そこから `Agent` インスタンスを取得してクエリを投げる」** という物理的なファイル制約があります。

これをクリアしつつ、本番コードとの密結合を断ち切るため、**「評価時に一時ディレクトリを作成し、評価種別・モードに特化した `agent.py` をその場で自動生成して配置する」** アプローチを採用しました。

### 設計とメリット
1. **完全な自己完結性**: 評価ランナー側（`SkillEval` クラス）が、評価対象のスキル・ワークフローのメタデータから最適なエージェント起動ファイルを都度動的生成するため、本番コードへの依存がゼロになります。
2. **`execute()` による完全なカプセル化（100% インプロセス実行）**: 評価実行の準備（設定ファイルの配置、一時フォルダの生成）から、ADK評価サービス（`LocalEvalService`）のインプロセスでの初期化・非同期タスクの実行・結果オブジェクトの集計まで、すべてのテスト実行フローは `SkillEval.execute()` （およびそこから委譲される `ADKEvalServiceRunner`）の内部にカプセル化されています。これにより、呼び出し側は `subprocess`（外部プロセス）の起動や結果 JSON のシリアライズ/デシリアライズを一切意識することなく、通常のメソッド呼び出しによってダイレクトに型安全な結果オブジェクト（`EvalRunResult`）を受け取ることができます。
3. **`use_mock` によるポリモーフィズム的な制御**: モックを使用するかどうかは、子クラス（`UnitEval` は `False` (通常実行)、`TriggerEval` は `True` (モック実行)）がプロパティ `use_mock` をオーバーライドして自律的に決定します。呼び出し側がモック化の制御を意識する必要が一切ありません。

### 100% インプロセス実行の構成
ADK の `LocalEvalService` などの Python API を直接インプロセスで実行するため、低レベルなADK評価サービスの初期化、実行、イベントループ衝突回避のための同期化（`ThreadPoolExecutor` の適用）、および結果の集計ロジックは **`ADKEvalServiceRunner`** ([evaluation/runner.py](file:///workspace/edd-agent-tools/src/edd_agent_tools/evaluation/runner.py)) にカプセル化されています。これにより、コントローラーである `SkillEval.execute()` メソッドはスリムで保守性の高い状態を維持しています。

### モック実行と通常実行の思想的使い分け

ADKおよび評価駆動開発（EDD）では、テストの「関心事の分離」を最大化するため、テストの目的（分類）に応じてモックを使用するかどうかを厳格に切り分けます。

| 評価パターン | 主な検証目的 | 実行ポリシー | 思想的根拠（なぜそうするのか） |
| :--- | :--- | :--- | :--- |
| **Trigger Check** | LLMのツール呼び出し意思決定 | **モック実行 (Mock)** | 検証の焦点は「LLMがツールを呼ぶべき状況で正しく呼び出せるか」です。ツールの内部バグや外部環境に影響されず、LLMのインテント（呼び出し意図）のみを純粋かつ高速にテストするため、ツール実行をモックで遮断します。 |
| **Eval-as-Unit-Test** | ツールコードの実装の正しさ | **通常実行 (Real)** | 検証の焦点は「ツールのPython実装そのものが正しい値や軌跡（Trajectory）を出力するか」です。ツール自体をモック化してはコードの動作をテストできないため、通常実行でロジックを検証します。 |

## 3. ワークフローエージェントの規約統一

ワークフロー全体の評価をダイレクトかつクリーンに行うため、以下の規約を新たに義務化・統一しました。

### 統一規約
> モジュールタイプが **`WORKFLOW`** のパッケージ（例: `workflow-generator`）は、そのエントリーポイントである **`scripts/__init__.py`** から、**`workflow_agent`**（`Agent` オブジェクト実体）を必ずエクスポート（公開）しなければならない。

### 動作フロー
1. 動的生成される評価用の `agent.py` は、対象が `ModuleType.WORKFLOW` であることを検知すると、そのパッケージの `scripts/__init__.py` から `workflow_agent` を直接インポートします。
2. インポートした `workflow_agent` をそのまま `adk eval` にエクスポートします。
3. これにより、中間エージェントが噛まない「ダイレクトなワークフロー評価」が可能となり、二重ラッパー問題が完全に解消されます。

---

## 4. テンプレートファイルによるコード管理とフォルダ構成の整理

動的生成するコード文字列 of ハードコーディング（ヒアドキュメント）を排除し、より安全かつ堅牢にするために以下のリファクタリングを実施しています。

1. **`evaluation/` パッケージフォルダへの整理**:
   Python 組み込みの `eval()` 関数との混同を避けるため、旧 `evaluation.py` ファイルを廃止し、**`edd_agent_tools/evaluation/`** パッケージフォルダ配下に評価関連クラスやアセットを集約・再配置しました。
2. **物理テンプレート（`*.py.tmpl`）による管理**:
   エージェント起動用のコードひな型を **`evaluation/templates/`** 配下に物理ファイルとして分離しました：
   - `eval_agent_skill.py.tmpl`（スキル評価用）
   - `eval_agent_workflow.py.tmpl`（ワークフロー評価用）
   - `eval_mock_setup.py.tmpl`（モックアタッチ用）
3. **安全なプレースホルダー置換**:
   `SkillEval` 内では、パッケージ相対パスから解決されたテンプレートファイルをロードし、標準文字列フォーマット（`.format()`）を用いて必要なプレースホルダー（`{skill_name}`, `{skill_root}` など）のみを安全にバインドします。これにより、インデントエラーやエスケープの問題といった動的生成時のバグのリスクを最小化しています。
