# skill-coder 設計思想 (Design Philosophy)

このドキュメントは、`skill-coder` および ADK 2.0 スキル開発におけるコアな設計思想、アーキテクチャの原則、および AI（SkillDeveloperAgent）へ向けたコーディングのガイダンスをまとめたリファレンスです。

---

## 1. 外部純粋関数インターフェースと内部オブジェクト指向設計の融合

ADK 2.0 規約との整合性と、実装のメンテナンス性を高めるため、「外部向けには純粋関数として公開し、内部的にはオブジェクト指向（クラス設計）で処理をカプセル化する」ハイブリッド構造を採用しています。

* **純粋関数エントリーポイント (handler.py)**:
  外部に公開される窓口（ツールの呼び出し口）は、[scripts/handler.py](file:///workspace/src/skills/skill-coder/scripts/handler.py) 内の単一の純粋関数（`def skill_coder(...)` など）として定義されます。この関数は引数と型アノテーションを完全に明示し、ビジネスロジックは持ちません。
* **オブジェクト指向エグゼキューター (executor.py)**:
  実際のビジネスロジックは、[scripts/executor.py](file:///workspace/src/skills/skill-coder/scripts/executor.py) の `SkillExecutor` クラスにカプセル化されます。ハンドラー関数から引数を受け取ってインスタンス化され、対象の具象メソッド（例: `skill_coder(...)`）を通じて処理を実行します。プレースホルダーとしてこの構造を置いておくことで、AIに「ビジネスロジックを適切にメソッド分割・カプセル化して実装する」よう誘導します。

## 2. 仕様概要（What）と追加要望（How）の分離マージ

設計書ファイル（`design.json`）に記録される静的な情報と、実行時に人間から与えられる動的な指示を、役割（意味論）に応じて明確に分離し、LLM へと安全に伝達します。

1. **仕様概要 (`summary`) [What]**:
   * そのスキルの本質的なビジネス目的や本来あるべき役割・仕様を、`design.json` の `summary` フィールドに静的に記録・永続化します。
   * これにより、既存コード改修時に「コードから仕様概要をLLMに毎回推論させる（非決定論的ブレが生じる）」ことを防ぎ、一貫した基本仕様（What）を静的マスターデータとして提供します。
2. **実装の追加要望 (`prompt`) [How]**:
   * コマンド引数として動的に渡される `--prompt` は、既存設計に対する「差分改修のこだわり」や「今回の具体的な実装指示」として扱います。
3. **エグゼキューター内でのマージ**:
   * `SkillExecutor` 内部で、静的概要（What）と動的要望（How）を以下のように区分けして結合し、LLMにインプットとして引き渡します。
     ```python
     full_prompt = f"=== 基本仕様概要（What） ===\n{design_data.summary}\n\n=== 今回の実装・改修要望（How） ===\n{prompt}"
     ```

## 3. 入出力（I/O）スキーマの定義思想とモデル対称性

外部（フレームワーク、CLI、あるいは他スキル）から渡されるパラメータはすべて、関数のシグネチャ（引数リスト）として型安全に明示されます。

* **通常のスキルとワークフロー型スキルの「対称性」**:
  * ツール（`tool`）とワークフロー（`workflow`）で外部向け API の対称性を 100% 確保します。どちらも、エントリーポイントは個別引数を受け取る純粋関数（`def function_name(arg1, arg2) -> [固有Outputモデル名]`）とし、明確な出力モデルを戻り値型とします。これにより、呼び出し側は内部実装詳細を意識せずに対称的な呼び出しが可能です。
* **入力パラメータの型安全**:
  * スキルの引数は、`handler.py` 内の関数のシグネチャとして明示的に宣言されます。これによって、ADK 2.0 の `FunctionTool` は自動的にツールの JSON Schema を構築でき、型安全な呼び出しを保証します。
* **出力モデル（固有のOutputモデル）による構造化応答と models.py の独立**:
  * 処理結果は、必ず Pydantic (V2) のそのスキル固有の出力モデル（例: `SkillCoderOutput`, `GenerateSkillSpecOutput` 等）のインスタンスとしてカプセル化して返却されます。
  * `handler.py` と `executor.py` の間での**循環参照（Circular Import）を完全に排除するため**、出力モデルクラスの定義は専用の **`models.py`** ファイルに物理的に独立させます。
  * 静的解析ツールやエディタでの**コード補完（静的型ヒント）の恩恵を100%受けるため**、`executor.py` や `logic.py` 等の手書きロジック内では、`from .models import Output` のような曖昧なエイリアスは使用せず、`from .models import GenerateSkillSpecOutput` のように**固有の具象モデルを直接インポートして戻り値型アノテーションに指定します。**

## 4. 公開APIの最小化とカプセル化

ライブラリ共通規約（カプセル化の原則）に基づき、スキルのパブリックAPI（パッケージの外部へ露出される公開インターフェース）は、自動生成される `__init__.py` の属性解決ハンドラ経由で露出されるエントリーポイントとなる純粋関数 (例: `skill_coder` や `generate_skill_spec` など) **のみに厳格に制限されます。**

外部の呼び出し元（他ノードやワークフロー）は、動的な状態マージ機構（`merge_result_to_state`）によって結果を受け取るため、スキルの出力モデルクラスをインポートする必要はありません。そのため、`__init__.py` から出力モデルクラス（`Output`）は一切エクスポートしません。

これら以外の、開発者が自律的に設計・作成するモジュールや `SkillExecutor` 自身は、パッケージ内部の実装詳細（プライベート）としてカプセル化し、決して外部へエクスポートしてはなりません。

---

## 5. ポータビリティの確保と sys.path 汚染の完全排除

スキルの独立性とポータビリティを保証するため、スキルパッケージ内の Python コード（`__init__.py` や `handler.py` 等）には `sys.path.insert` などの動的なパス解決操作を決して記述してはなりません。

* **グローバル名前空間（sys.path）の汚染防止**:
  * スキルフォルダ内に `sys.path` を操作する副作用（side effect）が含まれると、同じランタイム上で他のスキルをロードした際、同名モジュール（`models` や `handler`）の競合・衝突（シャドーイング）や、複雑な循環参照を引き起こします。
* **相対インポートへの統一とフレームワークへの委ね**:
  * スキル内部でのモジュール間参照は、すべて **相対インポート（例: `from .models import GenerateSkillSpecOutput`）** に統一します。
  * スキルごとの隔離された仮想名前空間の登録やインポートパスの管理は、フレームワーク（`edd-agent-tools` の `Skill.load_module`）が一元的に管理・解決します。これによって、スキル自体は完全に受動的かつポータブルな（再利用性の高い）パッケージになります。

## 6. ブートストラップロードの安全性担保

スキル初期ロード時（AIエージェントによる自動生成が始まる前の、`executor.py` などの AI生成ファイルがディスクにまだ存在しない初期化フェーズ）において、インポートエラーによるシステムのクラッシュを防ぐため、`__init__.py` にて `__getattr__` を定義し、外部からツール関数が要求された時点で初めて、`handler.py` から対象の関数をダイナミックにインポートして返します。これによって、まだロジックが未実装の状態でもロード時の安全性が確保されます。
