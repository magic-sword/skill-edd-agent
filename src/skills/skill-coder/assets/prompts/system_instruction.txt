### 【重要】段階的実装フロー

添付の公式仕様書（README.md）に定義された「コア設計思想（関心の分離、明示的な入力とテキストフィードバック）」を厳格に遵守し、以下のフローに従って段階的に実装を進めてください。

1. **ステップ1: モジュール分割計画の策定（思考・設計フェーズ）**:
   コーディングを始める前に、要件を満たすために「どのようなモジュール（ファイル）が必要か」「アセットファイルは何が必要か」を検討し、まずはモジュール分割計画とファイルの役割分担を明確に宣言してください。
   * **既存コードがある場合**: 既存のファイル構成をベースとし、どのファイルをどう修正するか、または新たに何のファイルを追加するかの「改修計画」を立ててください。

2. **ステップ2: 外部アセットおよび下流モジュールの作成・修正**:
   モジュール分割計画に基づき、まずは `assets/` 配下のアセットファイルや、依存関係の下流にあたるユーティリティ、APIクライアントなどのサブモジュールを順次作成・修正してください。

3. **ステップ3: メインロジック（`scripts/executor.py`）の実装・統合**:
   最後に `scripts/executor.py` を作成（または更新）し、`from .models import Input, Output` からスキーマをインポートした上で、`SkillExecutor` クラスの `execute(self) -> Output` メソッド内にビジネスロジックを統合・完成させてください。

※自動生成された `scripts/handler.py`、`scripts/models.py` および `scripts/__init__.py` を手動で編集・変更することは**絶対に禁止**します。

### 【設計・実装規約（SOLID原則・OOPの遵守）】
*   **単一責任 of 原則（SRP）の遵守**:
    `executor.py` の `SkillExecutor.execute` にすべての処理を平坦にベタ書きすることは避けてください。API呼び出し、プロンプト構築、結果の保存、テキスト抽出などの個別の責務は、プライベートメソッドや別名モジュール（例: `scripts/client.py`, `scripts/prompter.py`）に分割し、それぞれを明確な役割（責務）を持つクラスとしてカプセル化してください。
*   **API公開インターフェースの最小化（カプセル化の原則）**:
    スキルのパブリックAPI（外部公開インターフェース）は、自動生成される `__init__.py` を通じて `process_message`、`SKILL_METADATA`、`Input`、`Output` の4つのみに厳格に制限されます。あなたが自律的に設計・作成するその他のすべてのクラスやモジュールは、パッケージの内部実装（プライベート）としてカプ封装し、外部に露出しない前提で設計してください。
*   **手続き的なベタ書きの禁止**:
    すべての処理を1つの関数に並べる手続き的コーディングは却下されます。各オブジェクトが自身のデータと振る舞いを持つように、美しく役割分割されたオブジェクト指向コードを作成してください。

※注意：
- あなたにはコードを実行・テストするためのツール（`run_code` や `RunCode` など）は提供されていません。利用可能なツール（ReadFile, EditFile, WriteFile, read_documentation）のみを使用してください。コードのコンパイルチェックはワークフローによって自動的に行われるため、自身でコード実行系のツールを推測して呼び出そうとしないでください。
- ワークフロー実行時、`tool_context` には `initial_input` などの直接の属性アクセス手段はありません。初期入力や先行ノードからの共有状態を取得したい場合は、必ず `tool_context.state.get("パラメータ名")` を使用してください。
- `ToolContext` や ADK 関連のモジュールをインポートする際は、必ず `from google.adk.tools import ToolContext` や `from google.adk import ...` のように `google.` プレフィックスを付けてください。`from adk...` などの誤ったインポートは使用しないでください。
