# skill-designer 設計思想 (Design Philosophy)

このドキュメントは、`skill-designer` および ADK 2.0 スキル設計・再設計におけるコアな設計思想、設計メタデータ管理の原則、および AI（SkillDeveloperAgent）へ向けた設計ガイダンスをまとめたリファレンスです。

---

## 1. 宣言的メタデータ設計 (Metamodel-driven Design) と「LLMのハーネス」としての役割

スキルの振る舞い、インターフェース、制約、およびエージェント向けガイドラインは、直接ソースコードにハードコーディングするのではなく、まず **`design.json`（設計書）に宣言的メタデータとして定義・集約されるべきである**という原則です。

### 「LLMのハーネス（Harness/制御具）」としての意義
LLMは非決定論的で創造的ですが、自由度が高すぎるためにインターフェースを歪めたりハルシネーションを起こしたりするリスクを常に孕んでいます。`design.json` は、LLMの挙動を安全に制御・ガイドするための強固な「ハーネス」として機能します。

* **決定論的な器の先制配置**:
  * LLMにコードや仕様書を出力させる**前**に、まず `design.json` で引数の名前、型、バリデーション制約を決定論的に固定します。
  * 後続のステップ（`skill-coder`, `skill-spec-writer`）は、この固定されたメタデータ（器）を基に、ハンドラーの骨組みやパラメータ表をプログラムの処理によって決定論的に先んじて書き出します。
* **限定された自由度の提供**:
  * LLM（Gemini）は、この決定論的に防衛された構造（ハーネス）の内部を埋める（ビジネスロジックの実装や、機能概要の肉付け）という、**安全に制限された枠内においてのみ非決定論的な創造的推論を許されます。**
  * これにより、LLMによる構造の「破壊」を物理的に防ぎ、システムとしての信頼性と型安全性を極限まで高めています。

### メタデータの動的同期と永続化
* **ソースコードと設計書の動的同期**:
  * `skill-designer` は、アタッチされたソースコード（特に `handler.py` 等の公開関数のシグネチャおよび引数型ヒント）から、パラメータの型定義や説明文を自律的に解析し、`design.json` のメタデータにマッピングします。
* **`PromptField` によるプロンプトメタデータの永続化**:
  * `is_prompt_parameter: true` であるプロンプト用引数がソースコードに定義されている場合、その引数に対する「指定可能な指示（`prompt_instructions`）」や「構造的な制約（`prompt_constraints`）」も、Gemini のコードスキャン解析を通じて自動的に `design.json` のパラメータ属性として抽出し、永続化します。これにより、マニュアルの自動インジェクション機能へと情報がシームレスに伝達されます。

## 2. 実行タイプ（`execution_type`）の厳格な分類原則

AIエージェントがスキルを実行・発見する際の行動方針を最適化するため、`execution_type` は以下の基準に基づいて厳密に分類されなければなりません。

1. **`"agent"` (エージェント思考型)**:
   * **基準**:
     * スキルの入力パラメータに、LLMの推論を引き出して思考させるためのプロンプト用引数（`is_prompt_parameter: true` な引数、例: `prompt`, `requirement` など）が1つ以上含まれている場合。
     * スキル内部でLLM（Gemini API等）を呼び出し、テキスト生成、コード生成、設計、要約、思考推論などの創造的・非決定論的な処理を中核としている場合。
   * **特徴**: 仕様書（`SKILL.md`）において、親エージェントが「自身の推論能力を駆使して成果物を作る」ための思考プロセス（Instructions）が生成されます。
2. **`"tool"` (決定論的ツール型)**:
   * **基準**:
     * 入力パラメータがすべて単純なデータ（ファイルパス、数値、フラグ、文字列の完全一致など）のみであり、LLM用の動的なプロンプト引数を一切受け取らない場合。
     * スキル内部の処理が、ファイルの保存、CLIコマンド実行、データ処理など、100%決定論的（推論を必要とせず、常に再現性がある）なスクリプト処理のみで完結している場合。
   * **特徴**: 仕様書において、親エージェントが「無駄な推論を挟まず、引数を渡して一発でツールを起動する」ための薄い指示書が生成されます。

## 3. 仕様概要（`summary`）フィールドの優先解決

スキルの自己ドキュメンテーション能力を一貫して保つため、`design.json` に **`summary`** フィールドを定義し、基本仕様概要（What）のマスターデータとして管理します。

* **人間の意思（オーバーライド）の最優先**:
  * `skill-designer` の実行時、オプション引数 `--summary` が明示的に指定された場合、Gemini の自動要約出力をバイパスし、**人間が指定した概要テキストをそのまま `summary` フィールドに優先保存**します。
  * これにより、基本仕様がLLMのゆらぎによって勝手に改変されるのを防ぎ、人間が意図した通りの概要説明を固定維持できます。
* **新規作成時の自動要約**:
  * `--summary` が未指定の新規作成時には、Gemini が `--prompt` の内容から本質的なビジネス目的を要約した1〜2文を自律生成して `summary` に設定します。

## 4. スキル設計書（design.json）の出力と下流ツール群への連携

`skill-designer` は、設計結果としての **`design.json` ファイルを物理的に出力（配置）する役割**を担います。このファイルは、下流の開発ツール群にとって設計情報の唯一の真実のソース（Single Source of Truth）となります。

* **コード自動生成（skill-coder）への連携**:
  * 出力された `design.json` をインプットとして、後続の `skill-coder` が `executor.py` (class SkillExecutor) や `models.py` などの Python コードファイルを物理的に配置・実装します。
* **仕様書自動生成（skill-spec-writer）への連携**:
  * `skill-spec-writer` が仕様書（`SKILL.md`）を自動生成する際にも `design.json` がロードされ、定義されたパラメータテーブルや `summary`（仕様概要）が決定論的にマークダウンへ展開されます。
* **OOP設計の整合性の担保**:
  * 設計書において入力モデルや実行タイプをオブジェクト指向の規約に適合した状態で書き出すことで、`skill-coder` が安全に `executor.py`（`class SkillExecutor` の骨組みプレースホルダー）を決定論的に初期配置できるよう、スキーマの整合性を担保します。
* **責務の分離 (SRP) の誘導**:
  * 設計データを通じて、AIコーダー（LLM）に対して、ロジックを平坦に並べるのではなく、`SkillExecutor` クラスを中心としてプライベートメソッドや別クラスへ適切にカプセル化してオブジェクト指向的（SOLID原則に準拠）に実装するように指示を誘導します。

## 5. ADKの2段階ロード思想に準拠した高精度な設計プロセス（L1ディスカバリ ➡ L2詳細マッピング）

ADK 2.0 が採用している「メタ情報（L1）で存在を検出し、トリガー後に詳細（L2）を動的ロードする」というオンデマンドな思想を、`skill-designer` 自体の設計フェーズにも適用しています。これにより、ワークフロー設計時のハルシネーションを極限まで低減しています。

### 1段階設計におけるハルシネーションの課題
従来の 1回のLLM呼び出しによる設計アプローチでは、システム内の全スキルの詳細仕様を最初からLLMに与えるとコンテキストが破綻し、逆に与えないとLLMが既存スキルの名前や引数仕様を知らないため、以下のような問題が発生していました。
* 既存のスキル呼び出しであるにもかかわらず、適当なカスタム関数（`type: "function"`）として定義してしまう。
* 依存スキルの引数名や戻り値のキーをLLMが捏造（ハルシネーション）し、接続不整合（型エラーや属性エラー）を起こす。

### L1 ➡ L2 の動的2段階設計プロセス

この課題を解決するため、`skill-designer` では以下の2段階生成プロセスを採用しています。

1. **第一段階（L1ディスカバリ: 骨組み設計）**:
   * 現在システムに登録されている全スキルの **L1メタデータ（名前、トリガー条件・説明）のみ** をコンテキストとしてLLMに提示します。
   * LLMは各スキルの引数などの詳細には触れず、「ユーザーの要件に対して、どの既存スキルをどのステップで接続すべきか」の判断だけに集中し、`steps` の骨組み（`type: "skill"`, `target: "対象名"`）を正確に決定します。
2. **第二段階（L2精緻化: 詳細引数マッピング）**:
   * 第一段階でLLMが「使用する」と決定したスキルのみをプログラム側が自動検知し、それらのスキルの **詳細な `design.json`（入力引数の型や説明、出力される戻り値仕様）のみをオンデマンドでロード** してLLMに追加提示します。
   * LLMは目の前に厳密に提示された仕様をベースに、ワークフローの変数からステップ引数への紐付け（`inputs` マッピング）を正確に完成させます。

### 設計上のメリット
* **トークンの節約と注意のフォーカス**: 関係のないスキルの詳細情報はロードされず、LLMは「ツールの選択」と「値のマッピング」という関心事を順に分けて処理できます。
* **接続安全性の保証**: 依存する相手の正確なスキーマ仕様が提示された状態でマッピングが記述されるため、引数名や戻り値の捏造が原理的に発生しなくなり、下流プロセスでの他スキル呼び出しが100%安全かつ正確に結合されるようになります。

## 6. 契約駆動テスト（Contract-driven Testing）とテスト自動生成への適合

`design.json` に記述される仕様メタデータは、単なるドキュメントにとどまらず、スキルの品質保証プロセスにおける**「実行時契約（Contract）」**および**「テストデータ自動生成のマスターデータ」**としての役割を兼ねています。

### テストコードを生成しない「データ駆動型テスト」の実現
スキル毎に異なるテストコードを個別に生成・管理することは、テストコード自体のバグや仕様変更に伴うメンテナンスコスト（技術負債）の急増を招きます。これを解決するため、`design.json` を契約書として位置づけ、データ駆動による自動テストを実現します。

* **`example` による正常系テストデータのシード化**:
  * 各入力パラメータに `example`（正常系の代表的な入力例）を定義しておくことで、テストジェネレータは意味的なハルシネーションを起こさず、仕様に適合した正確なテストデータを瞬時に自動生成できます。
* **制約情報（Validation Rules）による異常系（境界値）テストの自動生成**:
  * `ge` / `le` (数値範囲)、`min_length` / `max_length` (文字長)、`pattern` (正規表現)、`choices` (選択肢) などの制約情報を基に、境界値の外側を狙うネガティブテストケースをルールベースで決定論的に自動生成します。
* **`response_type` による戻り値の自動アサーション**:
  * `output_mode` が `VALUE_ONLY` または `CONVERSATIONAL` の場合であっても、公開関数ごとに期待される戻り値のプリミティブな型（`response_type`）を定義します。
  * これにより、共通のテスト実行エンジン（Executor）が隔離環境（`LocalWorkspaceEnv`）で関数を呼び出した後、戻り値が契約通りの型と構造で返されているかを100%自動で機械的にアサーションできるようになります。

この設計思想により、開発者は個別のテストコードの管理から完全に解放され、`design.json` の仕様定義を正確に保つことのみに集中すれば、高精度なテストと品質保証が自動的についてくるクリーンな開発サイクル（EDD）が維持されます。
